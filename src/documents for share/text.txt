PTAF UI Automation – Changes & Usage Guide

Scope:
This document summarizes the non-breaking improvements made to our PTAF UI automation stack. It focuses on dynamic iframe/modal handling, reusable role-based locators, a rich assertion layer, and generic reusable steps.
No changes were made to Hooks or any PicoContainer wiring.

⸻

1) What’s new (at a glance)
	•	Dynamic modal/iframe resolution (non-breaking):
	•	Automatically targets the topmost/visible modal frame when multiple modals match.
	•	Works with existing step definitions; no changes required in features.
	•	Robust chain parsing for locators:
	•	Supports both " > " and "&gt;".
	•	Supports unnamed role segments (e.g., "Button" or "ROW") for first-match behavior.
	•	Assertion layer (UIAssert):
	•	Rich assertions mirroring ActionPerformer semantics, with clean overloads (page / iframe / nested).
	•	Centralized screenshot capture on failure (re-uses your existing failure flow).
	•	Generic reusable steps (optional glue):
	•	Single step class you can drop in to cover “millions” of cases (page, modal, nested iframes, bulk tables, placeholders).

⸻

2) Files touched / added

2.1 ElementActionImpl (updated)
	•	Location: com.ptaf.ui.action_performer.ElementActionImpl
	•	Key changes (non-breaking):
	•	Dynamic frame resolution in:
	•	private FrameLocator findFrameWithElement(Page page, String iframeSelector, String element, String key)
	•	private FrameLocator findFrameWithElement(FrameLocator parentFrame, String iframeSelector, String element, String key)
	•	Strategy:
	1.	Try the provided selector with :visible
	2.	Try the selector as-is
	3.	Fallback to well-known modal patterns:
	•	iframe[name^='iframeWindowModal']:visible
	•	iframe[frameborder='0px']:visible
	•	iframe[name^='iframeWindowModal']
	•	iframe[frameborder='0px']
	4.	Ultimate fallback: first match of the original selector
	•	Reverse order scan (last → first) to prefer newest/topmost modal.
	•	Chain parsing unchanged but tolerant: " > " and "&gt;", unnamed roles allowed.
	•	No public signature changes; all existing steps & YAML remain valid.
	•	Imports: ensure import com.microsoft.playwright.options.WaitForSelectorState; exists.

Recommended entries:

    documentTypeTextbox: "TEXTBOX_(type in document type name)"

  Modal:
    addBtn: "BUTTON_Add"
    previousBtn: "BUTTON_Previous"

	•	TEXTBOX_(...) → role TEXTBOX with name = (type in document type name).
	•	TITLE_... > IMAGE → .getByTitle("...").getByRole(IMG).
	•	BUTTON_Add / "BUTTON" (unnamed) are both supported; unnamed picks the first match.

4) How dynamic modal selection works (under the hood)

When you pass an iframe selector (e.g., "iframe[frameborder='0px']" or "iframe[name^='iframeWindowModal']"), the framework:
	1.	Tries selector:visible.
	2.	If none, tries selector.
	3.	If none, tries known modal fallbacks.
	4.	Finally, falls back to the first match of your original selector (legacy behavior to avoid breakage).

Within the matches, it scans from last to first, and picks the first where the first chain segment of your YAML element is visible. This naturally targets the newest/topmost modal, even if identical controls exist in multiple modals.

6) Do / Don’t

Do
	•	Keep using your existing step definitions and YAML — these changes are backward compatible.
	•	Use semantic roles in YAML (BUTTON, TEXTBOX, HEADING, TITLE > IMAGE, etc.).
	•	For modals, pass a generic iframe selector like "iframe[frameborder='0px']"; the framework will pick the right one.

Don’t
	•	Hardcode modal indices like (//iframe[...])[2].
	•	Duplicate fragile selectors in step code — put them in YAML with role chains.

7) FAQ

Q: Two modals both have "BUTTON_Add". Which gets clicked?
A: The topmost/visible modal that actually contains a visible "BUTTON_Add".

Q: Do I need to change my Hooks?
A: No. We made no changes to Hooks for these features.

Q: Will existing features or teams break?
A: No. All changes are additive/non-breaking. Public signatures stayed the same.

Q: Do I need to reauthor YAML?
A: No. Existing TYPE_value entries still work. You can optionally use unnamed role segments (e.g., "BUTTON") where first match is OK.
