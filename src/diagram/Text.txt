### **How to Use It: A Quick Guide**

The framework is built on a simple principle: **define your action once in a YAML file, then use it in your Gherkin tests.** The structure is the same for all three layers.

#### **1. UI Testing (with Advanced Chaining)**

You can now chain locators to find elements inside other elements (like a button in a specific table row).

* **Define in `elements.yml`:** Use the `>` symbol to create a chain.
    ```yaml
    user_table:
      # This finds the row for "Jane Doe", then the "Edit" button inside it.
      edit_jane_doe: 'ROW_Jane Doe > BUTTON_Edit'
    ```
* **Use in `.feature` file:** The test step is still simple!
    ```gherkin
    Then we click on user_table locator edit_jane_doe
    ```

#### **2. API Testing**

Build, send, and verify API calls with a clean, readable Gherkin flow.

* **Define in `api_requests.yml`:**
    ```yaml
    jsonplaceholder_requests:
      get_single_post:
        method: "GET"
        endpoint: "/posts/{postId}"
    ```
* **Use in `.feature` file:**
    ```gherkin
    @api
    Scenario: Verify a blog post
      Given I set the path parameter "postId" to "1"
      When I send a "jsonplaceholder_requests.get_single_post" request to the "jsonplaceholder" service
      Then the response code should be 200
      And the value of the JSON path "$.title" should be "sunt aut facere repellat provident occaecati excepturi optio reprehenderit"
    ```

#### **3. Database Testing**

Directly query the database to set up test data or verify outcomes.

* **Define in `db_queries.yml`:**
    ```yaml
    users:
      get_user_by_email: "SELECT * FROM users WHERE email = ?;"
    ```
* **Use in `.feature` file:**
    ```gherkin
    @db
    Scenario: Check for existing user
      Then I verify the database contains a record for query "users.get_user_by_email" with parameters "jane.doe@company.com"
    ```

### ✅ **Important: This is 100% Backward Compatible**

All of our existing UI tests will continue to work without any changes. You do not need to update old tests. This new functionality safely extends our current framework.

### **How to Run Tests**

We now have dedicated "Runner" classes. To execute a specific test suite, use the appropriate tags in your feature files (`@api`, `@db`) and run the corresponding runner from your IDE:

* **`TestRunner.java`** (for UI tests)
* **`ApiTestRunner.java`** (for API tests)
* **`DatabaseTestRunner.java`** (for Database tests)
